## Current architecture (as mapped)

```
index.html (form)
  → PREVIEW_PROMPT built in the BROWSER
  → POST /preview (worker = thin Anthropic proxy, Sonnet 4.6, 8k tokens)
  → preview JSON { cities+nights, teaser_day, local_picks }
  → user approves (regenerate is the only edit option)
  → POST /create-checkout — formData + approvedCities (= preview.cities verbatim) → KV → Stripe
  → Stripe webhook (sig verified) → Cloudflare Queue
  → fulfillOrder:
      buildPerplexityResearch (2 parallel sonar calls, optional)
      ITINERARY_PROMPT (~650 lines, 16 steps) → Sonnet 4.6, 32–64k tokens, 1 retry
      generateOverview + generateHiddenFinds (parallel post-gen calls)
      dedup + book-before-you-go backstop + tier-badge check (log only)
      verifyAndEnrichWithPerplexity → Google Places enrichment
      renderItinerary → KV HTML → n8n delivery email
```

What's good: queue + idempotency guard, streaming to dodge timeouts, tier-scaled token budgets, post-gen split for overview/hidden finds, graceful-degradation enrichment, failure alerts, Stripe sig verification. The bones are solid.

## THE NIGHT-ALLOCATION BUG — root cause

It's not one bug. It's three layers, and the deepest one explains why prompt patches haven't fixed it.

### Layer 1 — The rules are dead text in the paid generation
In `ITINERARY_PROMPT`, the ARRIVAL CITY RULE and DEPARTURE CITY RULE (worker.js ~2127–2128) live inside **STEP 2 — CITY SELECTION**, which the prompt explicitly tells the model to skip whenever an approved city plan exists:

> "APPROVED CITY PLAN — USE EXACTLY AS IS... Skip Step 1 night allocation"
> "STEP 2 NOTE: If approved cities are provided above, skip city selection entirely."

Every paid order has `approvedCities` (it's set from the preview at checkout). So **for 100% of paying customers, the arrival/departure rules are in a section the model is instructed to ignore.** Only the round-trip final-night rule has an explicit override clause (line 2066) — which is why that one works and this one doesn't.

### Layer 2 — At preview time (the only place the rule is live), the prompt contradicts itself
The preview prompt is where the city plan is actually decided, and it has three conflicts:

1. **HARD CAP vs. ARRIVAL/DEPARTURE RULE.** Step 1 says: "Never list a city with 0 or 1 night if its size classification requires more — cut the city instead." Step 2 says the arrival city MUST appear for at least 1 night. For a Large/Mega arrival city (Tokyo, Rome, Bangkok) on a short trip, those are mutually exclusive instructions. The model picks one at random per generation.
2. **"know" mode vs. the rule.** "cityPlanningMode 'know' → respect listed cities exactly" conflicts with "arrival city MUST appear" when the traveler's list omits the airport city.
3. **Step order.** Night allocation (Step 1) is instructed *before* city selection (Step 2) — the model allocates nights before it's told which cities are mandatory.

### Layer 3 — The model has to guess which city the airport code maps to
The prompt provides `Arrival airport: LIR`. The model must infer "Liberia." `airports.js` already contains `[IATA, city, name, country]` for every airport and is loaded in the browser — but the city name is never injected into the prompt or used in code.

### And zero code-level enforcement anywhere
`parsePreviewJson` checks JSON validity. `hasRequiredKeys` checks keys exist. Nothing anywhere checks:
- arrival city present with ≥1 night
- departure city present with ≥1 night (or last)
- `sum(nights) === calcNights(arrivalDate, departureDate)` ← also unvalidated; an 8-night plan for a 7-night trip ships

LLM instruction-following is probabilistic. A hard business rule enforced only by prompt text in a 9-step (preview) or 16-step (paid) prompt will fail some percentage of the time forever, no matter how much CAPS-LOCK it gets.

## Recommended fix (priority order)

### P0 — Validate + repair the city plan in code
This is the pattern already proven in this codebase (`deduplicateHiddenFinds`, `validateBookBeforeYouGo`) — extend it to the plan itself:

1. **Resolve airport → city name in code** using airports.js data (send it in formData from the browser; it's already there).
2. **After preview parse, validate:** arrival city in list with ≥1 night; departure city in list with ≥1 night as final stop (or within round-trip rule); nights sum matches trip dates; no 0-night cities.
3. **Repair programmatically, not with a re-roll:** missing arrival city → insert at position 0 with 1 night, decrement the largest allocation. Deterministic, free, instant. (Fallback: one short targeted repair call — "this plan violates rule X, return corrected JSON, change the minimum necessary.")
4. **Re-run the same validator server-side in `fulfillOrder`** before generation — the approved plan is client-supplied and currently trusted blindly.

Do this and the bug rate goes to zero regardless of what the model does.

### P1 — Clean up the prompt contradictions (reduces repair frequency)
- Add an explicit carve-out to the preview HARD CAP: *"Exception: arrival and departure cities may take 1 night even when below their class minimum — never cut them."*
- Same carve-out on "know" mode.
- Swap Step 1/Step 2 order in the preview prompt (select cities → then allocate nights).
- Inject the resolved city name: `Arrival airport: LIR (Liberia)`.
- Restate the two rules in one line immediately before the JSON schema (end-of-prompt instructions get more weight).

### P1 — Fix the dead text in ITINERARY_PROMPT
Either delete the arrival/departure rules from the skipped STEP 2 (they're noise), or give them an override clause like the round-trip rule has. Cleaner: enforce upstream (P0) and keep the paid prompt out of the city-plan business entirely.

## Broader audit findings

### A. Prompt-patch treadmill (architectural, highest long-term value)
The git log shows the pattern: content bug → prompt hardening commit → new bug → more hardening. `ITINERARY_PROMPT` is now ~650 lines / 16 steps with 10+ competing CRITICAL/HARD blocks. Every rule added dilutes compliance with every other rule — this is *why* rules get ignored, and it will keep getting worse.

Two structural options, in order of effort:

1. **Cheap (do now):** Move every deterministic rule out of the prompt and into validators — night sums, tier badges (currently log-only), meal-venue uniqueness (`buildMealVenueSet` already exists — use it as a post-check, not just prompt text), day-of-week venue matching (regex on venue name vs. calendar date — fully computable). Each rule removed from the prompt improves compliance of what remains.
2. **Bigger (consider later):** Split day-by-day generation into **one call per city**, run in parallel. City plan is already fixed pre-generation, so cities are independent. Smaller prompts → dramatically better instruction compliance, faster wall-clock (helps your LONG-trip queue timeout), and a failed city can retry alone instead of re-rolling a 64k-token generation. Cost: more calls, and cross-city dedup needs the used-venue set threaded through (you already have the helper).

### B. Quick API-level wins
- **No system prompt.** The persona + output contract ("expert travel planner", "JSON only") should be a `system` param, not the top of the user message.
- **No assistant prefill.** Prefill the response with `{` — kills markdown fences at the source and makes most of the parse-retry machinery unnecessary.
- **Temperature unset** on all Claude calls (defaults to 1.0). Perplexity calls set 0.2, Claude calls set nothing. For constraint-heavy JSON generation, test 0.3–0.5 — likely a free compliance gain.

### C. /preview is an open proxy (cost/abuse risk)
The prompt is built in the browser and `/preview` forwards **any request body** to Anthropic on your API key, with `Access-Control-Allow-Origin: *` and no rate limiting. Anyone who reads your frontend source can burn your Anthropic credits with arbitrary prompts at 8k tokens a pop.
Fix: accept only `formData`, build PREVIEW_PROMPT server-side (move it into the worker — it's already a shared module), allowlist model/max_tokens, add a per-IP rate limit (Cloudflare WAF rule is the zero-code option).

### D. Hardcoded advisory lists will rot
Level 3/4 country lists are frozen at "verified July 2026." In 6 months they're wrong in both directions. Options: monthly scheduled re-verify (you have Perplexity in the stack), or at minimum a recurring calendar reminder. Also: this list ships inside STEP 2, which is skipped for paid generations — safety text should live where it always executes (the overview post-gen call is a natural home).

### E. Product gap feeding the bug
The preview offers regenerate-or-pay — travelers can't edit nights or drop a city. Every plan defect becomes either a lost sale or a support problem. A simple nights-stepper + remove-city on the preview (with your validator enforcing arrival/departure invariants on their edits) turns the P0 validator into a feature, not just a guardrail.

### F. Stale docs
- SpringOS `CLAUDE.md` still says travel planner = Make.com ("already built, do not migrate") and routes travel planner work to `make-automation.md`. Reality: Cloudflare Worker calling Claude directly, n8n only for delivery email. Routing map + stack section need updating.
- No skill file exists for this worker's actual architecture (prompt locations, KV keys, queue flow, deploy via wrangler). Worth drafting given how often this project gets iterated.
